# 家庭代办 · 竞品对比与优化方向

> 状态：记录稿；**工程计划已开**（标准 App + Figma UI）  
> 记录日期：2026-09-30（2026-10-01 增补「标准 App」；工程按 W1–W4 / S2 / S3 推进）  
> 产品暂名：LuckyTodo  
> 对照基线：已实现能力（v003 + v004 主屏组件）与 `README.md`  
> **产品方向：标准 App**——云端注册账号、创建家庭、邀请家人；主路径不再要求用户自建 NAS。  
> **正式规格：** [v005-标准App-方案.md](../02-specifications/家庭代办/v005-标准App-方案.md)；UI 以 [Figma LuckyTodo UI 原型](https://www.figma.com/design/uwS6F2XKfZdCwMCa3jmBfy/LuckyTodo-UI-原型) 为准。

## 1. 结论摘要

LuckyTodo 要做的仍是 **家庭执行工具**（便签 / 待办 / 日程 / 计划打卡），但分发与账号模型从「自托管 NAS + 可选连接」改为 **标准云端 App**：

1. 用户注册云端账号（邮箱或手机）  
2. 登录后创建家庭，或通过邀请码 / 链接加入家人家庭  
3. 客户端默认连接官方服务器，**主路径取消「连接 NAS」**  
4. 离线缓存 + 同步、四种对象、角色权限、主屏组件尽量复用  

体验层短板（提醒可信、一秒记下、日历深度、孩子反馈、系统触达）仍然成立；在标准 App 下，**远程推送与正规上架** 从「受限可接受」变为「应纳入计划」。

**本期战略优先级：** 先完成「注册 → 建家 / 邀请 → 同步」闭环（S0–S1），再叠今日页与日历等体验优化（原 P0–P2）。

## 2. 产品定位与竞品坐标系

| 类型 | 代表产品 | 强项 | 与 LuckyTodo 的关系 |
|------|----------|------|---------------------|
| 个人待办 | Things、Todoist、滴答清单、TickTick | 自然语言、子任务、标签、远程催办 | 效率能力可借鉴，不宜做成完整个人 GTD |
| 家庭日历 | Cozi、TimeTree、系统日历 | 日/周视图、家人颜色、订阅日历 | 日历深度是明显可补短板；邀请加人是标配 |
| 家务 / 习惯打卡 | OurHome、朝暮计划、小习惯 | 连续打卡、积分、照片打卡 | 计划打卡可学「反馈」，刻意不做积分商城 |
| 系统全家桶 | 提醒事项 + 日历 + 家庭共享 | 推送、锁屏、Siri、Watch | 标准 App 应接入远程推送与上架分发 |
| 自托管 | Nextcloud Tasks、Vikunja、旧版 LuckyTodo NAS | 数据自有 | **不再作为主路径**；可作为远期「高级 / 自建服务器」选项 |

**转型后应保留的差异化：**

- 四种对象：便签、待办、日程、计划（含里程碑与多人打卡）  
- 角色权限与可见性（管理员 / 家长 / 成人 / 儿童）  
- 本机优先写入 + 同步队列（断网可记、可打卡）  
- iOS / Android 主屏组件  
- 家庭侧 AI 洞察 + 规则兜底（平台统一配额或订阅后开放）  

**转型后主动放弃的主路径卖点：**

- 「数据只在你家 NAS、用户自填 HTTPS」——改为云端托管；用隐私政策、导出、账号注销补信任。

## 4. 标准 App 转型计划（2026-10-01 确认方向）

### 4.0 目标形态

```text
云端用户账号（邮箱或手机，全局唯一）
  ├─ 创建家庭（成为管理员）
  ├─ 邀请家人（短码 / 链接 / 二维码）
  └─ 加入家庭后：同步便签、待办、日程、计划；角色权限沿用现有思路
```

**一期建议约束（降低复杂度）：**

- 一账号默认加入 **一个** 家庭（多人家庭通过邀请扩展成员，而不是一人挂多个家庭）。  
- 儿童不独立手机号注册；由家长创建儿童成员 / 儿童子账号。  
- 主路径 **不出现**「连接家庭服务器」；官方 `apiBase` 写死（或构建配置）。  
- NAS / 自建服务器：**不纳入标准 App 一期**；若保留，仅作远期高级选项（原方案 B）。

### 4.0.1 可选产品形态（已选主路径）

| 方案 | 说明 | 决策 |
|------|------|------|
| A · 纯云端标准版 | 注册 / 建家 / 邀请；无 NAS | **主选** |
| B · 云端 + NAS 双通道 | 默认云，高级可连自建 | 远期可选，一期不做 |
| C · 托管过渡版 | 先自建多租户云，暂缓上架 | 可作为 S1 工程落地方式 |

### 4.0.2 模型对照：现状 → 标准 App

| 现状 | 标准 App |
|------|----------|
| 本机账号可先于家庭；可选填 NAS URL | 必须云账号；无家庭则进「创建或加入」 |
| `members.username` 家庭内唯一 | 全局 `users` + 家庭内 `members`（用户在家庭中的身份） |
| `/api/setup/family` 整机初始化一家 | 登录后可创建家庭；一服务多租户 |
| 管理员 `POST /api/members` 代设密码 | 邀请码 / 链接；被邀请人自己登录；儿童可由家长代建 |
| 客户端 `setApiBase` | 默认官方 API；隐藏或删除主路径填 URL |
| 全能签 + 本地通知 | 规划 App Store / 应用市场上架 + APNs / FCM |

### 4.0.3 可复用 vs 必改

**高复用：** 四种对象与权限、离线写 + sync、计划打卡与里程碑、洞察概念、Capacitor 与 Widget 桥。  

**必改：** 认证模型（user ≠ member）、家庭创建 / 邀请 API、去掉自定义服务器主路径、多租户存储与媒体、运维与合规。  

**宜新写：** 注册登录与邀请引导页、推送服务、运营向管理后台（封禁 / 排查）。

### 4.0.4 标准 App 分阶段（S 序列，优先于原体验 P 序列）

#### S0 · 产品决策锁死（短）

1. 注册方式：手机验证码优先，或邮箱+密码（可二选一先做一种）。  
2. 一账号几个家庭：一期锁定「一个」。  
3. 儿童：仅家长创建。  
4. 是否同期上架：可先 TestFlight / 内测包，但 API 按云端多租户做。  
5. 隐私与信任：隐私政策、数据导出、账号注销入口列入 S2，不拖到上架前一周。

#### S1 · 标准 App MVP（最小闭环，最高优先级）

验收：**陌生人装 App → 注册 → 创建家庭 → 发邀请 → 家人加入 → 共同待办可同步。**

1. 全局用户注册 / 登录 / 退出。  
2. 创建家庭；无家庭时空态：「创建家庭」或「我有邀请码」。  
3. 邀请：短码 + 可选链接；角色可指定（成人 / 家长）；过期与次数限制。  
4. 客户端去掉「连接服务器」主路径；写死官方 API。  
5. 保留现有 sync 与四种对象；管理员代建改为「添加儿童」辅路径，不再作为家人加入主路径。  
6. 本机旧数据：登录云账号后提示合并（沿用合并交互，文案改为云账号而非 NAS）。

#### S2 · 产品化（可上架的基本盘）

1. 远程推送（被指派、提醒、邀请结果）。  
2. 忘记密码 / 找回；账号注销；家庭数据导出。  
3. 媒体迁对象存储（OSS/S3）+ CDN；数据库规划 PostgreSQL（上量前可从多租户 SQLite 过渡）。  
4. 同步冲突 UI；基础监控与封禁。  
5. 隐私政策、用户协议、未成年人与家庭共享相关说明。

#### S3 · 增长与体验加深

1. 应用市场上架材料与审核通过。  
2. 叠原体验优化：今天页、便签转待办、日历日视图、打卡反馈等（见第 5、6 节）。  
3. 容量 / 人数限制与订阅预留。  
4. （可选）再开放「连接自有服务器」给极客用户。

### 4.0.5 标准 App 相关风险

1. 隐私卖点从「数据在自家 NAS」变为「数据在平台」——需政策与导出补信任。  
2. 一期若同时做云 + NAS 双模式，极易做不完。  
3. 上架后未成年人与家庭共享审核更严。  
4. 现有本机 / NAS 用户需迁移说明，避免静默丢数据。

## 5. 体验层不足与优化方向（在标准 App 之上继续做）

> 下列条目不替代 S1；在 S1 闭环可用后，按第 6 节与体验 P 序列穿插。

### 5.1 提醒与「出门在外」

**竞品：** 远程推送、贪睡、逾期再催、位置提醒。  
**我们（现状）：** 本地通知；全能签下无 APNs。  
**标准 App 后：** 远程推送进入 S2；本地通知仍作补充。

**优化方向：**

- S2 接入 APNs / FCM；被指派、到期提醒、邀请类通知。  
- 贪睡 / 延后 10 分钟；截止日当天二次轻提醒。  
- 同步前：仍可提示「有 N 条提醒待登记」，避免用户误以为未设置成功。

### 5.2 信息架构与「一秒记下」

**优化方向：**

- 便签独立入口，或「今天」固定置顶区 +「查看全部」。  
- 便签详情：转待办 / 转日程。  
- 全局搜索（四种对象）。  
- 轻量「清单」类型（买菜、出门前检查）。  
- 原生分享扩展 / 快捷指令：「分享到 LuckyTodo」。

### 5.3 日历深度

**优化方向：**

- 优先「日视图时间轴」。  
- 成员颜色区分参与人。  
- ICS 导入 / 导出或只读订阅学校日历。  
- App 内点空白快速添加。

### 5.4 计划 / 习惯执行

**优化方向（不必游戏化）：**

- 连续天数 / 本周完成环。  
- 打卡可选一张照片。  
- 家长端「今日谁缺卡」聚合卡片（沉到「今天」）。  
- 补卡：可选「仅家长可为孩子补一次」。

### 5.5 协作与家庭动态

**优化方向：**

- 邀请码 / 链接 / 二维码（由 S1 交付，不再限本 NAS）。  
- App 内「家庭动态」：谁完成了什么、谁新建了日程。  
- 同步冲突 UI：保留我的 / 用服务器的。

### 5.6 系统整合与触达

| 缺口 | 建议 |
|------|------|
| 远程推送 | S2 必做 |
| 锁屏 / 待机 / Watch | S3 后排队；锁屏小部件 ROI 较高 |
| 系统日历 | 可选「写入系统日历」副本 |
| 备份导出 / 账号注销 | S2 合规必做 |
| 应用市场上架 | S3；S1/S2 可用 TestFlight / 内测 |

### 5.7 工程与产品打磨

- `apps/web/app.js` 体量过大；转型期宜按认证 / 家庭 / 今天 / 同步拆分，避免继续堆单体。  
- 忘记密码走平台找回（不再仅「管理员重置」）。  
- AI 洞察：平台统一模型与配额；规则洞察沉到「今天」。  
- 头像裁剪、附件预览、冲突提示对齐默认预期。

## 6. 刻意不做或后置

与「三步打卡」或一期范围冲突的能力：

- 积分商城、家庭群聊  
- OT / CRDT 级实时协作光标  
- 完整项目管理（看板、依赖、复杂标签体系）  
- 语音群留言  
- **一期不做** 云端 + NAS 双模式  
- **一期不做** 一账号多家庭  
- 公开商店作为唯一分发可后置于 S3，但 API 与账号模型按上架产品设计  

说明：云端「多家庭租户」（很多家庭共用一套官方服务）是标准 App **必做**；上表「多家庭」指 **同一用户账号同时加入多个家庭**，一期不做。

## 7. 建议排期（合并版）

### 第一优先级 · 标准 App 闭环（S0 → S1）

1. 锁死注册方式与「一账号一家庭」。  
2. 用户注册 / 登录。  
3. 创建家庭 + 邀请加入。  
4. 客户端默认官方 API，去掉 NAS 连接主路径。  
5. 同步与四种对象在新账号模型下跑通。

### 第二优先级 · 可上架产品化（S2）

1. 远程推送。  
2. 找回密码、注销、导出。  
3. 对象存储与库表加固。  
4. 冲突 UI、基础合规文案。

### 第三优先级 · 每日打开率与家庭日历（原 P0 / P1）

1. 「今天」：待办 / 缺卡 / 今日日程；缺卡置顶。  
2. 便签完整列表 + 转待办。  
3. 打卡连续天数 + 家长监督摘要。  
4. 日视图时间轴 + 家人颜色；全局搜索。

### 第四优先级 · 差异化加深（原 P2 / S3）

1. 打卡照片；轻量清单。  
2. 家庭动态流；洞察沉到今天。  
3. 锁屏组件 / 分享扩展；上架与订阅预留。  
4. （可选）自建服务器高级模式。

## 8. 验收时怎么判断有效

### 标准 App 闭环

| 信号 | 说明 |
|------|------|
| 零运维上手 | 用户不填服务器地址也能完成注册与同步 |
| 邀请可达 | 家人凭码或链接加入，无需管理员代设登录密码 |
| 多人一致 | 同一家庭两端待办 / 打卡联网后一致 |
| 儿童可控 | 儿童由家长创建，可见范围符合角色规则 |

### 体验优化（S1 之后）

| 信号 | 说明 |
|------|------|
| 打开即知今日 | 不点二级页也能看到待办、日程、缺卡 |
| 三步内打卡 | 孩子完成计划仍保持短路径 |
| 提醒可信 | 远程或本地提醒行为可预期 |
| 记下不丢 | 便签可找回、可转待办 |
| 家长可监督 | 一眼看到谁缺卡 |
